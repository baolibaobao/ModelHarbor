# ModelHarbor 开发流程

## 1. 总体方式

项目采用“风险优先的纵向切片”，每个阶段都形成可运行、可测试、可回退的增量。先证明流式代理、IPC、密钥保护、路由公平性和号池导入这些高风险部分，再增加大面积 UI 和更多协议。

每个阶段遵循固定循环：

1. 从产品规格提取本阶段验收用例。
2. 先写 fake upstream、夹具和失败测试。
3. 实现最小纵向链路。
4. 运行单元、组件和集成测试。
5. 提交变更摘要、测试结果、截图或 API 示例供审阅。
6. 审阅通过后再开始下一阶段。

禁止一次性铺开所有页面后再补核心逻辑，也禁止只用真实站点手工验证而缺少确定性夹具。

### 1.1 用户开始与验收门禁

每个细分任务都必须经过用户明确授权和验收，状态含义固定如下：

| 状态 | 含义 | 代理可执行动作 |
| --- | --- | --- |
| `pending` | 尚未开始 | 等待用户明确发送“进行 Sx.y”或等价指令 |
| `in_progress` | 用户已授权，正在实现 | 只执行该细分任务，不跨到其他任务 |
| `awaiting_acceptance` | 实现、测试和文档材料已准备好 | 停止继续开发，提交材料等待用户验收 |
| `completed` | 用户明确回复验收通过 | 允许进入下一个已授权任务 |
| `changes_requested` | 用户验收后提出修改 | 只修复用户指出的范围，完成后再次等待验收 |

规则：

1. 用户没有明确“进行 Sx.y”时，代理只允许整理文档、回答问题或准备验收材料，不得开始该任务的实现。
2. 任务达到技术完成后，代理必须停在 `awaiting_acceptance`，不能自动开始下一个细分任务。
3. 只有收到“验收通过 Sx.y”或明确等价表述后，才能把该任务标为 `completed`。
4. 一个大阶段只有在其全部细分任务均为 `completed`，并且用户明确验收该阶段后，才算阶段完成。
5. 用户提出修改时，任务进入 `changes_requested`；修改范围不得扩展到其他细分任务。

## 3. 阶段 1：工程骨架与技术验证

**本阶段已完成并通过审阅，仓库当前处于阶段 2。**

目标：建立可重复构建的双进程空壳，并尽早验证最关键的网络路径。

工作项：

- 初始化 Git、`.gitignore`、CMake Presets、vcpkg manifest 和版本信息。
- 建立 `modelharbor-desktop`、`modelharbor-gateway`、核心库和测试目标。
- 建立基础 Qt Widgets 窗口、Lucide 图标资源、浅色/深色 Token 和托盘。
- 建立当前用户命名管道，完成 ping、版本协商和状态订阅。
- 固化主窗口关闭决策：最小化到托盘继续运行，或优雅退出并停止网关；两条路径均有状态提示和测试夹具。
- 建立 fake upstream。
- 用 Beast + libcurl multi 完成最小 SSE 透传验证，覆盖背压、取消和断流。
- 建立格式化、静态检查、单元测试和 CI 命令。

退出条件：

- 新环境可用一条文档化命令配置、构建和测试。
- 桌面端能启动、发现、重启网关，并正确显示版本不匹配。
- 1 MiB 以上 SSE 夹具保持增量转发，客户端取消会取消上游。
- Debug/Release 均能打包启动，依赖许可清单自动生成。

阶段审阅重点：构建体验、双进程生命周期、基础 UI 风格和网络技术验证结果。

## 4. 阶段 2：数据、密钥与 Sub2API 导入基础

**当前阶段。S2.1-S2.6 继续执行细分任务开始与验收门禁。**

目标：先把本地数据模型、迁移、DPAPI 和号池导入事务做扎实。

工作项：

- 建立 SQLite 连接、迁移器、仓储和 WAL 参数。
- 实现 Site、Credential、Proxy、Channel、LogicalModel、Route 基础实体。
- 实现 DPAPI Secret Store、敏感字段 HMAC 指纹和日志脱敏器。
- 实现本地 API Key 创建、摘要校验、撤销与轮换。
- 实现 Sub2API `sub2api-data` v1、旧 bundle 解析。
- 实现 Codex 单对象、数组和 JSONL 解析。
- 实现导入预览、去重、冲突策略、代理引用和单事务提交。
- 实现账号池分组、标签、隐私模式、批量选择、导入前预检分类和后台可取消/继续的导入任务。
- 建立脱敏 Sub2API 测试夹具；后续再用用户提供的去敏样本做兼容回归。

退出条件：

- 数据库与日志扫描不到测试明文秘密。
- 每个导入条目都有新增、更新、跳过、冲突或错误结果。
- 任意条目失败时按配置选择整批回滚或跳过坏条目，行为有测试固定。
- 中断导入不产生孤立记录；重复导入结果幂等。
- 从空库和上一 schema 版本迁移的测试通过。

阶段审阅重点：数据字段、导入预览、冲突策略、凭据掩码和备份语义。

账号池交互验收：添加账号必须支持 OAuth、Token/JSON、API Key、本地导入四种入口的统一预览；批量任务必须能区分可导入、异常、已存在、无效，并能只提交选中条目、后台运行、取消和继续。

- 请求 ID、标准错误结构、超时、取消、大小上限和 usage 解析。
- 请求实验室的指定渠道模式与路由模式。

阶段审阅重点：API 兼容、错误展示、实验室交互和基础性能。

## 6. 阶段 4：账号池、路由与自动切换

目标：实现用户特别要求的同优先级轮流使用、账号池调度和有限故障转移。

工作项：

- 候选过滤与结构化过滤原因。
- 优先级分组、主备、严格轮询、SWRR 和最少负载。
- 原子并发 lease、总截止时间、已尝试集合和重试预算。
- Closed/Open/HalfOpen 熔断与 429 冷却。
- New API 兼容模式的账号/渠道自动禁用、HalfOpen 探测和自动启用；手动停用优先。
- 路由游标快照和进程重启恢复。
- 路由解释 UI、实时并发和冷却状态。
- 将阶段 2 导入且存在适配器的账号加入真实候选池。
- 按已确认矩阵实现第一批 Sub2API 订阅账号适配器，包括刷新、过期、usage 和错误分类。

退出条件：

- 3 渠道 300 次严格轮询达到 `100 ± 1`。
- 5:3:2 权重 1000 次请求分布误差不超过 1%。
- 32 并发和 Thread Sanitizer 可用环境下无竞争问题；Windows 侧有压力回归。
- 渠道失败、冷却、熔断、恢复和跨优先级回退都有确定性测试。
- 401/403、`invalid_grant`、模型不存在、429、超时和 5xx 的自动禁用作用域正确；自动启用不会打开手动停用渠道。
- 首字下发后的流式错误不会拼接第二渠道响应。
- 第一批 Sub2API 账号从导入、验证到真实调度形成闭环。

阶段审阅重点：公平性报告、失败矩阵、Sub2API 兼容矩阵和路由解释。

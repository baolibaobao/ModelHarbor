# ModelHarbor 产品规格

## 1. 产品目标

ModelHarbor 解决四个连续问题：

1. 把分散的站点、Key 和订阅账号放入一个本地资源池。
2. 用统一模型名和一个本地 Key 对外提供 OpenAI-compatible API。
3. 持续知道每个渠道是否可用、速度如何、映射是否可疑、实际成本如何。
4. 在明确的优先级和轮询规则下自动选路，并能解释每次选路结果。

第一版面向 Windows 单机用户。所有配置、凭据、日志和统计默认只保存在本机。

## 2. 产品原则

- **先正确再扩协议**：先完整做好 `/v1/models` 与 `/v1/chat/completions`，再增加其他协议。
- **调度可解释**：每次请求记录候选过滤原因、最终渠道、重试次数和熔断状态。
- **测量口径固定**：所有延迟使用单调时钟；首字指首个有效内容事件，而不是 HTTP 响应头。
- **成本标注证据**：实扣、账单差分与响应估算必须分开展示。
- **导入先预览**：号池文件先解析、校验、去重和展示变更，确认后再入库。
- **默认保护隐私**：默认不保存请求正文与模型回答；日志中的凭据全部脱敏。

### 3.2 后续兼容阶段

- OpenAI Responses（首版不实现；后续阶段增加独立的请求/响应映射、流式事件和 usage 兼容测试）。
- Anthropic Messages。
- Gemini 原生协议。
- Embeddings、图片、音频、视频与 Realtime。
- 局域网监听、细粒度本地 Key 权限和多用户模式。
- 跨设备同步、远程控制面和外部数据库。

后续阶段采用适配器追加，站点、凭据、渠道、逻辑模型和路由的核心模型保持稳定。

### 3.3 首版协议边界

首版对外只承诺以下两个 OpenAI-compatible 端点：

| 端点 | 首版状态 | 说明 |
| --- | --- | --- |
| `GET /v1/models` | 实现 | 返回当前存在可调度候选的逻辑模型 |
| `POST /v1/chat/completions` | 实现 | 支持流式和非流式，保持 SSE 顺序和 `[DONE]` |
| `POST /v1/responses` | 后续 | 首版不接受该路径；后续以独立适配器和兼容矩阵加入 |

文档、实验室和验收测试不得把 Responses 当作首版已支持能力。首版可以在内部保留协议扩展点，但没有对应适配器、测试夹具和错误语义前，不对外开放。

## 4. 主要页面与工作流

### 4.1 总览

- 顶部状态栏固定显示网关运行状态、本地地址、今日请求、成功率和当前告警数。
- 主区显示最近 24 小时请求趋势、渠道健康表和最近异常。
- 快速操作只保留新增渠道、复制本地地址、打开实验室和立即巡检。
- 统计采用紧凑表格与小型趋势图，不堆叠装饰卡片。

### 4.2 渠道

表格列：启用、名称、类型、站点、凭据尾号、模型数、优先级、权重、并发、自动禁用策略、状态、最近 TTFT、今日请求、今日费用。

渠道编辑页保留 New API 风格的基础开关和调度字段：`enabled` 控制用户手动启用状态，`auto_disable_enabled` 控制错误触发的自动停用，另有错误阈值、冷却时长、自动探测间隔和自动启用开关。手动停用与自动停用必须显示为不同状态，避免用户误以为后台会自动恢复手动操作。

新增或编辑流程：

1. 选择协议适配器和输入 Base URL。
2. 填入或选择凭据；保存后只显示掩码和尾号。
3. 测试站点连通性并获取模型列表。
4. 配置逻辑模型到上游模型的映射。
5. 配置优先级、轮询权重、并发上限和超时。
6. 保存并选择是否立即加入路由。

### 4.3 模型库

- 合并展示逻辑模型、上游模型、所属渠道和最近状态。
- 支持按模型名、站点、标签、协议和健康状态筛选。
- 同一逻辑模型展开后展示所有候选渠道、映射名、价格和能力指纹。
- `/v1/models` 默认只暴露至少存在一条可调度渠道的逻辑模型。
- 可配置“保留展示暂时冷却模型”，但必须带状态说明。

### 4.4 健康中心

检测分两层：

1. **站点检测**：DNS、连接、TLS、HTTP、鉴权和模型列表接口。
2. **模型检测**：实际发起最小 Chat 请求，验证协议结构与有效输出。

每次记录：

- 开始时间、结束时间、HTTP 状态和错误分类。
- 连接时间、TLS 时间、首个有效内容时间、总耗时。
- 请求模型、响应报告模型、输出是否非空、流是否正常结束。
- 输入、输出、缓存读取、缓存写入和推理 Token；缺失字段标记为未知。
- 本次预计成本和探测预算消耗。

批量检测支持并发上限、单项超时、取消、失败重试和预算上限。后台巡检默认使用低频低 Token 请求，避免探测本身形成明显费用。

### 4.5 请求实验室

- 渠道模式：指定某一渠道，绕过自动路由，便于定位问题。
- 路由模式：通过本地网关发起，验证真实调度链路。
- 支持 `stream`、temperature、max_tokens、system prompt 和自定义 JSON 扩展字段。
- 响应区展示渲染文本、原始 JSON/SSE、响应头、usage、错误和路由轨迹。
- 正确性校验包含 HTTP 状态、Content-Type、JSON/SSE 结构、有效文本、finish reason 和 `[DONE]`。
- 支持期望文本的“包含、完全相等、正则”断言，供快速回归使用。

### 4.6 能力指纹

能力指纹是多项测试的证据集合：

| 测试项 | 证据 |
| --- | --- |
| 基础协议 | 流式事件、finish reason、usage 字段完整度 |
| JSON 输出 | 指定 schema 后能否稳定返回可解析结构 |
| 工具调用 | tool_calls 结构、参数 JSON、并行调用能力 |
| 上下文 | 分档递增的上下文输入是否成功，记录可验证下限 |
| 输出长度 | 实际稳定输出长度，不把声明值直接当结果 |
| 多模态 | 支持时验证图片输入；首版可显示“未测试” |
| 推理特征 | reasoning usage、参数接受度和响应行为 |
| 身份线索 | 响应 `model` 字段与自述，仅作低权重证据 |

结果分为“符合预期、部分符合、明显异常、证据不足”，并展示每项原始证据。测试包有版本号，历史结果必须关联测试包版本。高 Token 测试在执行前显示预计成本。

### 4.7 倍率与费用核算

标准成本按 Token 桶计算：

```text
基准成本 = 普通输入Token * 输入单价
         + 缓存读取Token * 缓存读取单价
         + 缓存写入Token * 缓存写入单价
         + 输出Token * 输出单价
         + 其他可计费Token * 对应单价

有效倍率 = 观测实扣成本 / 基准成本
缓存命中率 = 缓存读取Token / 输入Token
```

内部金额统一使用整数微美元或定点十进制，禁止使用二进制浮点直接累计金额。

证据等级：

| 等级 | 数据来源 | 展示名称 |
| --- | --- | --- |
| A | 单请求实扣字段，或请求前后余额的隔离差分 | 实扣倍率 |
| B | 上游账单接口在隔离时间窗内的用量差分 | 账单倍率 |
| C | 响应 usage × 已配置价格 | 估算倍率 |
| U | usage 或价格关键字段缺失 | 证据不足 |

余额差分测试必须串行执行，测试窗口内锁定目标凭据，记录汇率、价格表版本、差分时间和误差来源。若上游只返回聚合账单，界面不得标成单请求实扣。

### 4.8 账号池与 Sub2API 导入

#### 4.8.1 账号池页面与添加账号

账号池页面采用平台分区 + 统一筛选模型：

- 按平台、账号类型和自定义分组展示；支持标签、搜索、状态、过期时间、配额和最近验证结果筛选。
- 提供 Compact、List、Grid 三种密度视图；默认使用适合批量操作的 List 视图，万级记录使用 Model/View 和分页。
- 每条账号显示掩码标识、平台、分组、标签、验证状态、配额摘要、并发上限、优先级和当前是否加入 API 服务；隐私模式隐藏邮箱、账号名和代理信息。
- 支持批量选择、批量验证、批量启用/停用、批量加入或移出路由、批量标签和批量分组。

“添加账号”入口先选择来源，再进入对应表单：

1. OAuth/重新认证：启动平台适配器定义的回环地址回调或设备流程，桌面端只显示状态，凭据由网关保存；不得为 OAuth 在局域网开放监听端口。
2. Token/JSON：粘贴或选择 JSON，先解析字段和来源，再进入预览。
3. API Key：填写供应商、Base URL、API Key 和可选代理，保存前支持连通性与模型列表检测。
4. 本地导入：选择文件或目录，自动识别 Sub2API、Codex JSON/JSONL 等格式。

每种入口都可以设置目标分组、备注、标签、代理、并发上限、优先级、倍率和高级选项；保存后可选择“仅保存账号”或“验证后加入 API 服务”。

#### 4.8.2 批量导入任务

批量导入是可观察、可取消的后台任务，不阻塞主窗口。任务分为“读取与解析、规范化、预检、预览、提交、后台验证”六步，预检结果至少分为：

- 可导入：字段完整、格式有效且未发现重复。
- 异常：可解析但存在过期、代理缺失、字段不完整或适配器暂不可用等问题。
- 已存在：根据稳定去重键匹配到现有账号，显示更新差异。
- 无效：格式、凭据形态或数值范围不满足要求。

预览页支持全选/反选、按状态筛选、逐条查看掩码和不可逆指纹、选择冲突策略、批量标签、目标分组，以及“提交后加入 API 服务”。提交后任务可继续在后台执行；用户可取消、稍后继续或打开任务详情查看逐条结果。取消必须停止未开始的工作，并让已提交事务保持一致，不留下孤立代理或半条账号。

首版解析：

- `type = sub2api-data`、`version = 1` 的备份结构。
- 旧 `sub2api-bundle` 结构。
- 账号字段：name、notes、platform、type、credentials、extra、proxy、concurrency、priority、rate_multiplier、expires_at。
- 代理字段及账号到代理的引用。
- Codex 会话的单对象、数组、嵌套常见结构和逐行 JSON。

导入流水线：

1. 在内存中解析并识别格式与版本。
2. 校验必填字段、凭据形态、代理引用和数值范围。
3. 通过平台、账号 ID、邮箱哈希、Token 指纹等建立去重键。
4. 预览“新增、更新、跳过、冲突、暂不可调度”结果。
5. 用户选择冲突策略：保留现有、仅补空值、使用导入值。
6. 单事务写入；敏感字段立即转为 DPAPI 密文。
7. 后台做低成本凭据检查和模型发现。

导入成功与“可被网关调度”是两个状态。所有记录都可保存和导出；只有存在运行时适配器且验证通过的账号才进入候选池。

导入任务条目至少区分 `parsed`、`normalized`、`preflighted`、`previewed`、`stored` 和 `rejected`；账号运行状态至少区分 `validating`、`verified`、`schedulable`、`blocked`、`expired` 和 `unsupported_runtime`。UI 必须同时显示导入状态与调度状态，不能用单一“成功”标签覆盖两者。

Sub2API 账号类型的运行时兼容矩阵在开发前锁定。首批真正进入 `schedulable` 的顺序建议如下：

1. **OpenAI-compatible API Key**：字段稳定、模型发现和 Chat Completions 验证成本最低，作为首个完整闭环。
2. **OpenAI/Codex 会话账号**：覆盖 OAuth/Token 刷新、过期和账号配额，是首批号池的核心类型。
3. **Anthropic/Claude 会话账号**：在独立适配器中完成刷新、模型映射、429 和 usage 解析后进入调度。
4. **Google/Gemini 会话账号**：完成 OAuth、项目/配额和模型能力差异验证后进入调度。
5. **Grok 及其他平台账号**：先完成导入与状态展示，适配器稳定后再开放 `schedulable`。

每增加一种账号类型，必须包含 Token 刷新、过期处理、模型映射、usage 解析、429 冷却、并发控制和脱敏测试；仅完成导入界面不算交付。

### 4.9 路由策略

路由按以下顺序执行：

1. 根据逻辑模型找到渠道候选。
2. 过滤禁用、未验证、模型不支持、凭据过期、并发已满、冷却中和熔断中的渠道。
3. 选择当前仍有候选的最高优先级组；数字越小优先级越高。
4. 在同优先级组内执行配置策略。
5. 请求失败时依据重试规则选择未尝试渠道。
6. 当前优先级全部失败后，才进入下一优先级。

同优先级策略：

- **主备**：稳定选择排序第一的健康渠道，失败后切换。
- **严格轮询**：每个路由 + 逻辑模型维护原子游标，按 A、B、C、A 顺序选择。
- **平滑加权轮询**：按权重长期收敛，并避免低权重渠道长时间饥饿。
- **最少负载**：按当前并发比例选择，得分相同时用轮询打散。

轮询游标只在成功取得并发槽位后推进。渠道被过滤时跳过但不重置全组游标。多线程并发下使用原子状态或串行调度器，禁止每个工作线程维护独立游标。

可选会话粘性默认关闭。启用后，界面明确提示它会改变逐请求严格轮询的分布。

### 4.10 重试、冷却和熔断

- DNS、连接、TLS、超时、429 和选定的 5xx 可进入故障转移。
- 401/403、`invalid_grant`、refresh token 失效等鉴权错误进入自动禁用状态；具体作用域由适配器错误分类决定。
- 流式请求在首个响应字节发送给客户端后不跨渠道重试，避免拼接两个模型回答。
- 非流式请求只有在客户端尚未收到响应体时重试。
- 单次请求记录已尝试渠道集合，防止循环。
- 默认最多尝试 3 个渠道，并受总截止时间约束，而不是每次重试重新获得完整超时。

熔断状态为 Closed、Open、HalfOpen：连续失败达到阈值后进入 Open；冷却结束只放行有限探测；探测成功后恢复。手动健康检查不应无条件清除真实流量触发的熔断历史。

### 4.10.1 自动禁用与自动启用（New API 兼容模式）

首版提供每个账号/渠道可配置的 `auto_disable` 策略，行为先兼容 New API 的渠道自动禁用工作流，再在后续阶段优化误判和恢复滞回：

| 错误类别 | 首版动作 | 作用域 |
| --- | --- | --- |
| 401/403、`invalid_grant`、refresh token 失效、账号撤销 | 立即自动禁用，移出所有候选；需要重新认证或替换凭据 | 凭据及其全部渠道 |
| 模型不存在、模型映射无效、协议能力不匹配 | 禁用对应映射，保留账号其他已验证模型 | 渠道模型 |
| 429、余额不足、配额耗尽 | 先进入带截止时间的冷却；在时间窗内连续达到阈值后自动禁用 | 渠道或账号，按适配器声明 |
| 连接、TLS、超时、选定 5xx | 记录失败并累加连续失败；达到阈值后自动禁用 | 渠道 |

首版兼容默认值为：鉴权错误立即禁用；429 使用短冷却并在窗口内连续 3 次触发自动禁用；连接、超时和选定 5xx 在窗口内连续 3 次触发自动禁用。阈值、时间窗、禁用时长和错误码列表都必须可配置，且由适配器提供默认值。

自动启用规则：

- `auto_disabled` 到达冷却截止后进入 HalfOpen，只允许一个低成本验证或模型发现探测。
- 首版兼容模式下一次探测成功即可恢复；后续优化阶段再增加连续成功次数、指数退避和抖动抑制。
- 鉴权错误必须先完成重新认证或凭据替换，再允许探测恢复；无效凭据不做无期限刷新重试。
- 用户手动停用的账号/渠道标记为 `manual_disabled`，后台探测只更新诊断，不自动启用。
- 每次状态改变都通过“事务提交 -> 新路由快照 -> 原子发布”生效，并记录触发错误、时间、作用域、探测结果和恢复原因。

UI 必须显示自动禁用原因、首次发生时间、下次探测时间、当前作用域和恢复方式；路由解释中使用 `auto_disabled_auth`、`auto_disabled_health`、`cooldown`、`manual_disabled` 等结构化原因。

### 4.11 使用统计

请求明细默认保存 30 天，日聚合长期保存，保留期可配置。默认记录：

- 请求 ID、开始时间、接口、逻辑模型、上游模型。
- 路由、渠道、账号的内部 ID 与显示名快照。
- 状态、错误分类、重试次数、是否流式。
- TTFT、总耗时、输入/输出/缓存 Token。
- 基准成本、观测成本、倍率证据等级和价格表版本。

请求正文、完整响应、Authorization、Cookie、OAuth Token 和代理密码默认不入库。

### 4.12 窗口与托盘生命周期

关闭主窗口时显示一次明确选择：

- **最小化到托盘并保持服务**：隐藏主窗口，保留托盘图标；桌面端继续订阅网关状态，网关继续监听本地 API。
- **退出软件**：桌面端向网关发送优雅关闭请求；网关停止接收新请求、等待有限期限内的活动请求结束、刷新统计并关闭数据库，桌面端随后移除托盘图标并退出。

用户选择可记忆并在设置中修改。网关关闭超时或桌面端异常退出时，桌面端下次启动必须显示上次状态；正常“退出软件”路径不得留下托盘进程。网关仍可被桌面端重启和重新连接，但这不改变“退出软件”会停止其子进程的默认语义。

## 5. 本地 API 行为

### 5.1 鉴权

- 本地 Key 使用 `Authorization: Bearer <LOCAL_KEY>`。
- Key 仅保存不可逆校验摘要；创建时显示一次。
- 默认至少生成一个管理员本地 Key，可随时轮换和撤销。
- 健康检查与 UI 管理 IPC 不复用客户端 Key。

### 5.2 `/v1/models`

- 返回逻辑模型列表，不泄露上游渠道或账号信息。
- `id` 为逻辑模型名，`owned_by` 固定为 `modelharbor`。
- 默认只返回当前存在可调度候选的模型。
- 列表带短时间内存缓存，渠道或映射变更时主动失效。

### 5.3 `/v1/chat/completions`

- 未配置映射时，逻辑模型名可直接作为上游模型名。
- 透传兼容字段；仅在需要模型映射、协议适配或策略执行时修改请求。
- 流式响应保留 SSE 顺序和 `[DONE]`，同时旁路解析 usage 与模型字段。
- 为每个响应添加 `x-modelharbor-request-id`；调试模式可添加渠道别名，默认关闭。
- 上游错误转换为 OpenAI-compatible 错误结构，并保留内部错误分类用于 UI。

## 6. 可量化验收标准

### 6.1 路由公平性

- 三个同优先级、同权重、始终健康的渠道执行 300 个串行请求，每个渠道命中 `100 ± 1`。
- 权重 5:3:2 的三个渠道执行 1000 个请求，分布误差不超过各自目标的 1%。
- 32 并发下无数据竞争、游标回退或单渠道长期独占。
- 任一渠道冷却后立即从候选中移除，恢复后在一个完整轮询周期内重新获得请求。

### 6.2 流式正确性

- 代理不缓冲完整回答；收到首个有效上游事件后尽快转发。
- SSE 事件顺序、UTF-8 分片、跨缓冲区行和 `[DONE]` 均通过测试。
- 首字下发后发生上游错误时关闭当前流并记录错误，不拼接第二渠道内容。
- 1 MiB 以上分片请求与长流式响应保持内存有界。

### 6.3 延迟与稳定性

- 本地空载转发的额外中位延迟目标低于 5 ms，P99 目标低于 20 ms；以固定本地上游夹具测量。
- GUI 线程不执行网络、数据库迁移、批量导入或大 JSON 解析。
- 网关异常退出后，桌面端能显示状态并重启；数据库保持可打开且迁移一致。

### 6.4 数据与密钥

- 数据库和日志中搜索不到测试用明文 Key、refresh token、Cookie 和代理密码。
- 导出文件在写入前明确标记是否包含敏感字段。
- 中断导入不会留下半批账号或孤立代理。
- 每个数据库版本都能从上一个正式版本迁移，并有自动化测试。

### 6.5 指标正确性

- TTFT 从发出请求到首个有效内容事件计算，使用 `steady_clock`。
- 总耗时从发出请求到完整响应结束或错误终止计算。
- Token 未返回时显示未知，不用字符数伪装精确 Token。
- 费用计算覆盖普通输入、缓存读、缓存写、输出和已知扩展桶，并固定价格表版本。

## 7. UI 视觉与交互约束

- 默认窗口适配 1280×800；最低支持 1100×700，并检查 150%/200% 缩放。
- 使用左侧紧凑导航、顶部运行状态和可排序表格；弹窗只用于编辑、导入预览和高成本测试确认。
- 图标采用 Lucide，不使用 emoji 作为正式导航图标。
- 卡片圆角不超过 8 px，不做卡片套卡片，不使用大面积渐变和装饰光斑。
- 表格使用等宽数字、固定行高、列显示配置和虚拟化模型，保证万级日志可滚动。
- 状态不只依赖颜色，必须同时有图标或文字。
- 敏感字段默认掩码，复制和临时查看是明确动作。
